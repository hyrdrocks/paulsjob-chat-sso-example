Layout: put the chat where you want it

TL;DR — By default the widget is a floating pill with a card above it, over your page. Pass layout: { mode: 'rail', anchor: { selector: '#hyrd-rail' } } and it becomes a full-height panel inside a node you own, in your own document flow, with your CSS deciding how wide it is. In that mode there is no hyrd launcher — you open it from your own button with window.HyrdWidget.open(). mode and anchor have no default value: say nothing and nothing changes; name a rail and you must also name its anchor.

This guide is for third-party integrators embedding the widget on your own site. It documents the options.layout surface, the public window.HyrdWidget API, and the two CSS rules that keep your layout honest when the widget is not there. If you also need auto-login, see the SSO integration guide.

The three modes

One knob picks the shape, per page, from your own snippet. It is a desktop distinction: below 768px all three converge on the same full-screen chat.

ModeWhat you gethyrd launcherWhatsApp CTA
floating Today's pill plus a 530px card above it, both position: fixed over your page. paintedif your tenant enabled it
wide The full-bleed sheet. Same thing your recruiter's desktop_wide setting already produces — this is its first-class spelling, pill retained. paintedif your tenant enabled it
rail A full-height panel flush to one edge, in a node you own or as a fixed overlay. nevernever
!
A rail with no trigger of your own is unreachable, and that is by design. The mode removes the pill; it does not add a fallback, an edge tab or a reopen affordance. If you pick rail you must wire a button to HyrdWidget.open().

The knob table

Everything the rail introduced lives in a first-class options.layout, beside theme and never inside custom_widget_config. It is read once, at init, is never sent to the chat iframes, and is never stored on your tenant — it is a per-page decision in the snippet, so the same tenant can have a rail on the dashboard and a pill on the marketing site.

KeyTypeDefaultNotes
layout.mode 'floating' | 'wide' | 'rail' NO DEFAULT Absent defers to the older spellings — see precedence.
layout.anchor 'viewport' · { element } · { selector } NO DEFAULT rail only. Omitting it on a rail is refused, not defaulted. element wins if you pass both.
layout.side 'left' | 'right' 'right' rail only. Which edge the panel occupies.
layout.width number (px) 530 Viewport anchor only. Supported 320–640; outside that you get one warning and your number, never a clamp. On a container anchor the width is your stylesheet's.
layout.closeButton boolean true rail only. false is honoured on desktop only — the mobile overlay covers your own trigger, so it always keeps its way out.
★
mode and anchor have no default value, and that is deliberate. A literal 'floating' default would outrank the older spellings and silently revert every tenant using the wide sheet back to a 530px card, so absence has to mean “defer”, not “floating”. And neither anchor is a defensible guess on your behalf: defaulting to a container needs a node nobody gave us, and defaulting to the viewport would drop an overlay on a page that could have reflowed. If you write mode: 'rail', write an anchor too.

Keys that do not apply to the mode you picked — anchor, side, width or closeButton on a non-rail mode, or width on a container anchor — are reported and ignored, never silently reinterpreted. The widget still mounts.

Which spelling wins

There are three ways to ask for the wide sheet, because two of them predate this surface. One rule: the newest present spelling wins; anything absent defers.

TierSourceCan produce
0options.layout.modefloating · wide · rail
1options.desktopWidewide · floating
2your tenant's custom_widget_config.desktop_wide (+ its URL whitelist)wide · floating

Passing a tier-0 key alongside an older one warns and never throws — that is exactly what a mid-migration snippet looks like. layout.mode wins, and the console tells you the older key is now inert so you can delete it with confidence. rail can only ever come from tier 0: your tenant settings have none of these knobs.

The imperative API

One singleton, window.HyrdWidget. It is the same API in every mode — rail removes the pill, it does not add the API — so switching modes never changes your JavaScript.

MethodReturnsWhat it does
init(options)—Boots the widget.
startWidget(options)—Permanent alias of init. It will never be renamed.
open()—Opens the chat. Takes no arguments.
close()—Closes it, and cancels any pending auto-open.
toggle()—The obvious thing.
isOpen()booleanReads the current state synchronously.
on(event, fn)() => voidSubscribes. The return value unsubscribes.
destroy()—Removes the frames, the listeners and the rail wrapper.
updateTheme(theme)—Restyles the running widget.
verifyToken(token)PromiseSSO sign-in — see the SSO guide.
setToken(token)PromiseAdopt a session your page already holds.
clearToken()PromiseDrops the widget's session.

Events are ready, open, close and auth. The trigger state catalogue is exactly open or closed — there is no unread count and no “agent is typing”, because the pill has never had either. auth is a lifecycle event, not a trigger state.

Every method is safe to call at any time

  • Before the widget is ready, calls are remembered as desired state, not a log. Three open() calls before ready open the widget once; a close() after them leaves it closed. You never need to poll for an init flag.
  • Before ready, isOpen() answers with what you asked for, not false, so a trigger painted from it on first paint agrees with the click that caused it.
  • Against a destroyed widget every method logs one warning and no-ops. It never throws inside your click handler. Calling init() again revives it.
  • ready always precedes any open — including the opens that happen with no action from you (the timed auto-open, and the ~150ms open when the page carries a login_token). A listener attached in your ready handler cannot miss the first transition.
!
A refused init never fires ready. If your anchor fails one of the preconditions below, init aborts before any network call — no frames, no fetch — and the console error is the only signal. A trigger you gated on on('ready') correctly never lights up.

Painting your trigger, race-free

on() emits pure transitions and never replays; isOpen() is the reconciliation. Emission is synchronous, so subscribing and reading in one tick cannot miss a transition and cannot read a stale value. No retry loop, no polling.

// The documented recipe. All three lines in one tick.
const offOpen  = window.HyrdWidget.on('open',  () => paint(true))
const offClose = window.HyrdWidget.on('close', () => paint(false))
paint(window.HyrdWidget.isOpen())   // reconcile whatever happened before you subscribed

function paint(open) {
  button.setAttribute('aria-expanded', String(open))
  button.textContent = open ? 'Close assistant' : 'Ask the assistant'
}

// Both return an unsubscribe — call them when your component unmounts.
onUnmounted(() => { offOpen(); offClose() })

The container-anchor contract

This is the mode the rail exists for: you name a node you already render, and the chat appears inside it, in your own document flow, with your own layout squeezing to make room.

The whole contract is one appendChild and one remove():

  • We append exactly one child to your node and never write a style, a class or an attribute on the node itself. Your node stays yours; your CSS is never fighting an inline style of ours.
  • Your CSS owns width and height. Our child is 100% / 100%, so a media query, a CSS custom property or a transition: width you already wrote just works. There is no ResizeObserver and no layout message crossing the iframe boundary.
  • The child we append carries class="hyrd-rail-sdk" and three attributes you can select on: data-hyrd-layout="rail" | "overlay", data-hyrd-side="left" | "right" and data-hyrd-anchor="container" | "viewport".

Pass the node as an element or a selector

// Whichever your framework hands you at the moment you call init.
layout: { mode: 'rail', anchor: { selector: '#hyrd-rail' } }
layout: { mode: 'rail', anchor: { element: railRef.value } }

// Both? `element` wins — a reference cannot go stale, a selector can.

The four preconditions

Checked synchronously at init, before any network call. Every check is a read (querySelectorAll, getComputedStyle, a bounding rect), so a refusal cannot itself damage the page it refuses. Fail any one and nothing mounts.

#The node must…Why
1be empty This is what makes :empty trustworthy as “the widget is gone”. It is the CSS predicate, exactly: comments are fine, a whitespace text node is not. Write <div id="hyrd-rail"></div> with nothing between the tags.
2have no ancestor with a transform, filter or will-change Any of those makes the ancestor the containing block for position: fixed, which traps every overlay the chat paints — dialogs, drawers, the mobile sheet — in the wrong box.
3have a flex or grid parent flex, inline-flex, grid or inline-grid. That is what squeezes the siblings when the rail opens.
4be full-height in that parent A rail is a full-height column. Measured, not read off a declaration — height: 100% under a parent with no resolved height is a lie the computed style still reports.

…and the ways a selector misses

  • Matches nothing — refused.
  • Matches more than one node — refused, and we say how many. We deliberately do not take the first match: that would make the chat's home depend on document order, so duplicating the node would silently move the chat instead of telling you.
  • Is not a valid CSS selector — refused.
  • An anchor object with neither a usable element nor a non-empty selector string — refused. So is an anchor that is not 'viewport' and not an object at all (anchor: '#rail' is the common typo).

The two CSS rules you write once

Both hang off the node you already own. Neither needs any JavaScript on your side, and neither has a breakpoint of yours in it.

/* 1. PERMANENTLY DEAD — the widget is not on the page. */
#hyrd-rail:empty { width: 0; }

/* 2. MOBILE — the rail became a full-screen overlay, so the column is redundant. */
#hyrd-rail:has([data-hyrd-layout="overlay"]) { width: 0; }

Presence in the DOM is the whole fail-safe. Our child is removed on destroy(), when the chat iframe 404s or your CSP refuses it, and when it fails to initialise within 15 seconds. All three leave your node :empty, so rule 1 collapses the column with no JS from you. A dead widget never leaves a blank column in your layout.

★
:empty means permanently dead. It never means closed. Closing hides our frame and leaves the child in place — so those two rules can never disagree about what an empty node means. Which makes the corollary explicit: collapsing a closed rail is your business, not ours. Listen for close, set your own class or attribute, and let your own transition: width animate it. We animate nothing, and we ship no edge tab or reopen affordance that would duplicate the trigger you already have.

The same :empty hook is the honest way to keep your trigger in step with the widget. In floating the trigger dies with the widget because it is the widget; in rail yours outlives it. One more rule fixes that:

/* A dead widget should not leave a live-looking button. */
.dashboard:has(#hyrd-rail:empty) .chat-trigger { display: none; }

The viewport anchor

If you cannot restructure your CSS to satisfy the four preconditions, opt into an overlay explicitly:

layout: { mode: 'rail', anchor: 'viewport', side: 'right', width: 530 }

You get a position: fixed full-height panel pinned to side, at layout.width px (default 530 — today's panel width, the one the chat's layout is already proven at). It reads no node of yours, so it has no precondition to fail. It stacks at your tenant's configured z-index where one is stored.

The supported width range is 320–640px. Outside it you get one console warning per page per bound and your number is honoured exactly as written — there is no clamp. We cannot enforce a range on a viewport you resize whenever you like, and enforcing it at runtime would mean writing on your layout, which this contract never does. There is no drag-to-resize handle in either anchor.

!
The overlay is the low-effort option, not the good one. It covers your content, and in our own measurements it hid exactly the page furniture the floating pill was hiding — plus the host's own trigger — with no scrollbar to recover it. A container anchor degrades your layout; the overlay occludes it. Prefer the container anchor if you can restructure at all.

Mobile

Below 768px — measured on the host viewport, document.documentElement.clientWidth, the same number every other breakpoint in the widget uses — all three modes converge on the one full-screen chat that already ships. Mode is a desktop-only distinction, and it needs one mobile story, not three.

  • Our child becomes position: fixed; inset: 0 and says so: data-hyrd-layout="overlay". That attribute is what your second CSS rule reads — so there is one breakpoint, ours, and no second number of yours that has to agree with it forever.
  • The child is never re-parented. Moving an iframe reloads its document, and a phone crosses 768 on every rotation, so re-parenting would destroy a live chat session on a wrist flick. We restyle the node we already own; the iframe never reloads.
  • Your page's scroll is locked while the overlay is open, so the page does not slide around behind it. It is released the moment the chat closes, the frame dies, or you call destroy().
  • The close × is always painted here, even if you set closeButton: false: the overlay is sitting on top of your own trigger.
  • Tablets between 768 and 1024 get a real rail. The rail is never hidden on phones — deleting the chat is not a layout decision.

The rail's edge, and its close button

The rail uses your tenant's colours exactly as the floating card does — there is no second theming surface to configure. Its one visual difference is an edge: border-radius: 0, no shadow, and one border on the side-facing edge only (a rail on the right borders its left), so the panel reads as a panel and not as part of your page.

That edge ships as an ordinary author stylesheet rule, not an inline style, keyed on the published selector — precisely so you can override it when it disappears against your own background:

/* Ours, injected once into your document. */
[data-hyrd-layout="rail"] { border: 0 solid …; border-radius: 0; box-shadow: none; }
[data-hyrd-layout="rail"][data-hyrd-side="right"] { border-left-width: 1px; }

/* Yours — any of these outrank it comfortably. */
#hyrd-rail > [data-hyrd-layout="rail"] { border-left-color: #1f2937; }
★
Contrast against your page is yours to own — which is only an honest thing to say if you can act on it, hence a rule you can outrank rather than an inline style you cannot. Note that a CSS reset shipping *, ::before, ::after { border-width: 0 } (Tailwind's and UnoCSS's preflights both do) will delete our edge outright. Put it back with the selector above if you want it.

Moving the floating pill

Two knobs have always worked from the SDK and have never been written down. They are now the supported contract, and they keep their existing spellings: they live in theme, deliberately not mirrored into options.layout, which means exactly “the knobs the rail introduced”. This is a decision, not an oversight — please don't file it as one.

KeyValuesDefaultNotes
theme.position 'bottom_right' · 'bottom_center' · 'bottom_left' 'bottom_right' Which corner the launcher and its card occupy. Your value overrides your tenant's.
theme.custom_widget_config.desktop_button_space number (px) 30 The launcher's offset from both edges, on desktop. Mobile uses a fixed 8px. 
window.HyrdWidget.startWidget({
  company: 'acme',
  theme: {
    position: 'bottom_left',
    custom_widget_config: { desktop_button_space: 24 },
  },
})

A position outside the three-value enum gets one warning and the default corner — it can no longer reach a CSS string as "undefined", throw, or silently do nothing, which are the three ways it used to fail. A bad value stored by your recruiter is clamped in silence: you cannot see their settings, so you are not blamed for them. Both are read at init, like layout — a later updateTheme() restyles the widget but does not move it.

!
Known limit: desktop_button_space: 0 is not expressible — a stored zero is how the settings represent “empty”, so it falls back to 30. A launcher flush to the corner is not currently reachable from either layer. Per-axis offsets, top placement and collision avoidance are not supported.

What the console tells you

Messages are always on in production — there is no debug flag, because a flag would mean being told about a misconfiguration only if you already suspected one. A correct integration emits nothing at all, so any message is signal. Every one is prefixed [hyrd-widget], leads with the key path as a greppable token, says its tier in words, passes the offending node or value as the second console argument so devtools highlights it, and ends with a link back to this page.

TierWhatConsoleOutcome
A Shape errors — unknown mode, wrong type, an illegal combination, an off-enum theme.position warn Key ignored, widget still mounts
B Anchor refusals — the four preconditions, a missing anchor, an unreadable anchor, and the selector misses error Nothing mounts, init aborts, ready never fires
C Width outside 320–640 one warn per bound, per page Your value is honoured, never clamped

A and C leave a working widget on the screen, which is feedback in itself. B is the only class with no other signal, which is why B alone is an error.

[hyrd-widget] layout.anchor.selector: '#hyrd-rail' matched 3 elements — a rail needs
exactly one. Nothing is mounted and `ready` never fires.
See https://hyrdrocks.github.io/paulsjob-chat-sso-example/widget-layout.html  <div id="hyrd-rail">

The second console argument is the offending element or value, so devtools lets you click straight through to it.

Worked example — a dashboard shell

A three-part page: a top bar with your own trigger, your content, and a rail node as the third child of a flex row. Copy it whole; it satisfies all four preconditions.

<!-- The shell. `#hyrd-rail` is EMPTY — no whitespace between the tags. -->
<div class="dashboard">
  <header class="dashboard__bar">
    <h1>Employees</h1>
    <button class="chat-trigger" type="button" aria-expanded="false">
      Ask the assistant
    </button>
  </header>

  <!-- The flex row. Your content squeezes; the rail is the third child. -->
  <div class="dashboard__body">
    <nav class="dashboard__nav">…</nav>
    <main class="dashboard__main">…your table, your pagination…</main>
    <div id="hyrd-rail"></div>
  </div>
</div>
.dashboard { display: flex; flex-direction: column; height: 100dvh; }
.dashboard__bar  { flex: none; display: flex; justify-content: space-between; }

/* Precondition 3: a flex parent. Precondition 4: the rail stretches to full height,
   which `align-items: stretch` (the default) already does for you. */
.dashboard__body { display: flex; flex: 1; min-height: 0; }
.dashboard__main { flex: 1; min-width: 0; overflow: auto; }

/* YOUR width, YOUR transition. The SDK animates nothing and never touches this node. */
#hyrd-rail {
  flex: none;
  width: 420px;
  transition: width 180ms ease;
}

/* Rule 1 — the widget is permanently gone (destroy, CSP, 404, ready timeout). */
#hyrd-rail:empty { width: 0; }

/* Rule 2 — below 768 the rail is a full-screen overlay, so the column is redundant. */
#hyrd-rail:has([data-hyrd-layout="overlay"]) { width: 0; }

/* Closing is YOURS. We only emit the `close` event; this is what collapses the column. */
#hyrd-rail[data-closed] { width: 0; }

/* And a dead widget should not leave a live-looking button. */
.dashboard:has(#hyrd-rail:empty) .chat-trigger { display: none; }

/* CAREFUL: a `transform`, `filter` or `will-change` on ANY ancestor of #hyrd-rail
   is precondition 2, and the rail will be refused. A hover lift on .dashboard, a
   `will-change: transform` left over from an animation — both bite. */
// Runs once your shell is in the DOM — the anchor must exist when you call init.
const trigger = document.querySelector('.chat-trigger')
const rail = document.getElementById('hyrd-rail')

const config = {
  company: 'acme',
  domain: 'https://acme.chatbot.app.paulsjob.ai',
  employee_mode: true,
  layout: {
    mode: 'rail',
    anchor: { selector: '#hyrd-rail' },   // or { element: rail }
    side: 'right',                          // the default; written for clarity
  },
}

// Boot. If the bundle is already there, start directly; otherwise queue the config
// and load it — the singleton exists the moment the script has evaluated.
if (window.HyrdWidget?.startWidget) {
  window.HyrdWidget.startWidget(config)
  wire()
} else {
  window.HyrdWidget = { readyQueue: [config] }
  const s = document.createElement('script')
  s.src = 'https://acme.chatbot.app.paulsjob.ai/sdk.iife.js'
  s.async = true
  s.addEventListener('load', wire)
  document.body.appendChild(s)
}

// From here every method is safe to call at any time. The widget is NOT ready yet —
// it is still fetching its config — and none of this has to wait for it.
function wire() {
  trigger.addEventListener('click', () => window.HyrdWidget.toggle())

  // One tick: subscribe, subscribe, reconcile. No polling, no retry loop.
  window.HyrdWidget.on('open',  () => setOpen(true))
  window.HyrdWidget.on('close', () => setOpen(false))
  setOpen(window.HyrdWidget.isOpen())
}

function setOpen(open) {
  trigger.setAttribute('aria-expanded', String(open))
  // The rail's collapse is ours to drive — the SDK leaves its child in place.
  rail.toggleAttribute('data-closed', !open)
}
★
The width above (420px) is an example, not a recommendation. At 1440×900 a 530px rail leaves 670px for a table that wants 880 — the toolbar wraps and columns drop — while 380px leaves 820px and the chat itself starts reading narrow. Both sides degrade smoothly in opposite directions, so the number is a trade-off only you can make, against your own users' screens. That is why it is your CSS and not our knob.
!
If you mount from a framework hook that runs on every route (a Nuxt client plugin on app:mounted, say), the rail lands on every route until you scope where you call init. layout is init-only — per-route scoping is where you call init, and there is no setLayout.

Limits and caveats

rail is not the escape hatch for a career page with furniture

It is tempting to reach for rail whenever the floating pill is over something important. It will usually not help. The container anchor's four preconditions bite hardest on exactly the pages that were not built with a shell — an ordinary marketing or career page has no full-height flex column to hand — and the viewport anchor occludes more than the pill it replaced, not less. The rail answers a dashboard's problem: a page that already has a shell, in-flow furniture and a trigger of its own. If your page is not that, move the pill with theme.position instead.

A caveat about inline styles on our frames

★
Inline styles on hyrd-owned frames are maintained by live effects and are not durable. If you write to the style attribute of one of our iframes or wrappers, an effect may overwrite it on the next theme change, resize or state transition. In rail, size your own anchor node instead — that node is yours, we never write on it, and our child simply fills it.

This is a caveat, not a contract: there is no enforcement, no tier, and nothing detectable at init. It is written down because it is the mistake that looks like it should work.

Not supported, on purpose

  • No setLayout and no runtime mode switching — layout is init-only.
  • No configurable mobile breakpoint. 768 is fixed.
  • No drag-to-resize handle in either anchor, no SDK-owned edge tab, no SDK-owned animation, and no SDK mutation of your layout.
  • No unread count and no “agent is typing” on the trigger. The state catalogue is open or closed.
  • None of these knobs are settable by your recruiter in the Paul's Job admin, and none of them reach our backend. An anchor names a node in a page no recruiter has seen.

FAQ

I changed nothing. Does upgrading the SDK change how my widget looks?
No. Absence of the new keys means today's behaviour, exactly — that is the whole reason layout.mode has no default.
My recruiter turned on the wide sheet. Will my snippet override it?
Only if you write layout.mode. If you do, it wins and you get a console warning telling you the tenant setting is inert on that page. Say nothing and their setting still applies.
Nothing rendered and there is a red message in my console.
That is a tier-B refusal: your anchor failed a precondition, or the selector matched zero or several nodes. The message names the key and highlights the offending element. Nothing mounted, no network call was made, and ready did not fire.
My rail node is a blank column and there is no chat in it.
You almost certainly have not written #hyrd-rail:empty { width: 0 }. Our child is removed when the widget dies (CSP, a 404, or the 15s initialise timeout), and that rule is what collapses the column afterwards.
My node was refused for “already has children” but it looks empty.
It has a whitespace text node. <div id="hyrd-rail">\n</div> is not :empty by the CSS definition, and if we accepted it your collapse rule would never match. Close the tag immediately.
Can I collapse the rail myself when it closes?
You must — nobody else will. Listen for close and drive your own node's width. We hide our frame and leave the child in place, so :empty keeps its one meaning.
Does the chat survive a phone rotation?
Yes. We never re-parent the wrapper across the breakpoint, precisely because moving an iframe reloads it. A rotation is just a resize.
Can I use the rail and SSO auto-login together?
Yes, they are independent. Add onStartAutologin and verifyToken() from the SSO guide to the same config object.
Why is there no error event when the widget dies?
Because it would need opting into, and the fail-safe must work for a host who wired no JavaScript at all. The DOM is the signal: our child is gone, so :empty matches.
